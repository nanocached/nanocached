Architecture

The clients do the clustering. Nodes store data, discovery servers track membership, and every routing decision happens in the SDK — so the data path has no extra hop.

The three roles

RoleHoldsOn the data path?
nanocached-nodeCache entries (memory-bounded, LRU)Yes — clients connect directly
nanocached-discoverySoft-state membership registryNo — consulted only at bootstrap and on refresh
SDK clientThe node list, R, and open connectionsIs the data path

An SDK bootstraps by connecting to any configured address. The server's handshake reply says whether it is a node or a discovery server; against a discovery server the client fetches the node list (which carries the replication factor R) and then talks to nodes directly.

Routing: rendezvous hashing

For each key, every node gets a score — fmix64(fnv1a(node-name) XOR fnv1a(key)) — and the nodes ranked by descending score are the key's owner list. The top-R nodes hold the key. A namespaced key hashes be32(namespace-length) || namespace || key in place of the bare key, so one namespace's entries still spread over every node and two namespaces' identical key names land on different ones; the default namespace keeps the bare form so existing placements survive an upgrade.

Rendezvous (highest-random-weight) hashing has a property that matters here: adding or removing a node never reorders the surviving nodes in any key's ranking. A new node takes exactly its share of keys and nothing else moves; a dead node's keys fall to the next owner that already holds a replica.

All six SDKs and the server implement this pipeline bit-for-bit and assert the same published test vectors, so a polyglot deployment routes identically from every language.

Replication

Writes fan out from the client to all R owners; the primary's result decides the operation, and a dead replica never fails a write. Reads go to the primary and fail over to the next owner only when the holder is unreachable.

Two self-healing behaviors close the failure gaps:

  • A node that is asked for a key it does not own (stale client routing) answers W; the client refreshes its node list and retries once.
  • A write whose primary just died fails its connection, which triggers the same refresh-and-retry — so writes recover as soon as discovery drops the dead node (bounded by the liveness timeout, seconds).
  • Every heartbeat acknowledgment carries the current member list, so the surviving nodes' own ring view follows that eviction within one heartbeat interval too — a key re-homed from the dead node is served by its new owner rather than answered W.
  • That same ring-view update triggers re-replication: rendezvous hashing's removal property means an eviction (or any leave) can only ever promote a node into a key's top-R, never leave a slot vacant, but nothing had sent that promoted node a copy — so at R ≥ 2 the cluster silently ran one replica short after the first failure, and a second failure on the sole remaining copy lost the key. Once a survivor notices the drop, the highest-ranked surviving old owner of each affected key streams it to the newly promoted owner(s) as a put-if-absent handoff (U's trailing A token — see Protocol), so a re-replication racing a newer client write on the receiver can never regress it. This runs independently of, and is ordered against, a join in progress: a join's sweep of its own dead-copy marks waits for any in-flight re-replication to finish first (so it can't reclaim a survivor's only copy of a key re-replication hasn't delivered yet), and a re-replication that starts while a join is running waits for the join to finish first, since the join changes the ring again.

These healers share one consistency model: each acts on a snapshot of membership taken when it starts, and no two of them coordinate. A planned leave (the SIGTERM decommission — see Deployment) computes its handoffs the same way, from one roster fetch as the drain begins. Two membership changes landing inside one drain window — two nodes scaled in at once, or an eviction while a third drains — can therefore leave keys transiently below R: each leaver picks entrants from a roster that still lists the other, so a key whose owners included both comes out of the double-leave one handoff short, and that double-leave case never arises when scale-in retires one node at a time. A put-if-absent handoff cannot overwrite a newer value that the receiver already holds, so reads keep landing on the surviving copies, and a key that does lose its last copy is a cache miss. But the handoff carries no version either: if two survivors hold different copies of a key and both re-replicate it to a fresh node, the first to arrive is kept and the other is refused, newer or not, so a key whose surviving copies disagree can be served with its older value. There is no anti-entropy sweep: the gap closes per key when a client rewrites it or its TTL turns it over, and a key that is only read stays as it is.

Two more ways copies come to disagree or go missing were measured in chaos runs that join, decommission and kill nodes back to back. The first is bounded by the ownership reclaim pass described below; the second has no confirmed cause and no code fix, and is accepted as it stands:

  • A client write that reaches a node a join has displaced releases that copy's dead-copy mark, so the mark sweep never reclaims it (the release is deliberate: a mark that outlives its value once deleted fresh writes). Such a copy is removed instead by the ownership reclaim pass: after a membership change (and once more when the 120 s grace moves past the previous membership) a node drops the keys it has owned under no membership discovery published to it during the last 120 s, provided no handoff write for a key it did not yet own under its adopted membership reached it in that time (a handoff write for a key it already owns counts, to the pass, as a client write) and it is not itself leaving, mid-handoff or still forwarding for a join. The pass is checked every 30 s but skipped while nothing it judges against has moved. Until then the node keeps more entries than its share of the keys, and if an eviction makes it an owner again inside that window the copy is live again — by design, since a membership that flips back within the grace is exactly what the grace waits for — so an old value can still come back and be served or re-replicated. Under back-to-back membership changes the pass keeps postponing and the leftovers look as they did before; they go once the cluster has been quiet for the grace.
  • A replica write refused by a live node (WrongNodeError, while the client's node list and the nodes' views of the ring disagree) is swallowed by the SDK, so the key sits on one copy until its next write. If the node holding that copy is decommissioned or killed first, the newest value is lost and the surviving owners serve the older one. How often this happens varies: earlier runs (Python SDK, Docker) saw about 15–17 % of writes with a replica leg refused, a later run on current main about 1.5 %, and the difference is not explained. Refreshing the node list and retrying does not cure it: with a freshly fetched list the same node refused again in over 99 % of the cases.

Both are repaired by the next write to the key; a key that is only read is not. Spreading the membership changes out does not remove the leftover copies of the first case, and how often a refused replica write happens when the changes are spread out has not been measured.

Liveness is binary, though: a node that is slow but still answering is never evicted, and every request that touches it waits out its round trip — with R copies on N nodes, about R/N of them. The SDKs' hedged reads (opt-in) send a read to the next owner once the primary has been silent for a configured interval and take the first answer, so reads route around a slow owner; writes cannot, since every copy must be written.

Node identity is a random per-process name, decoupled from the network address — routing hashes the name, connections use the address — so a node restarting on the same address is correctly treated as a new member.

Joining a node: staged handoff

Adding a node must not drop the keys it takes ownership of, so joins are orchestrated by discovery in stages:

  1. The joining node registers; discovery tells the existing nodes to migrate the keys the newcomer now owns.
  2. While migration runs, existing nodes keep serving those keys and forward concurrent writes to the joiner, so no update is dropped. The forward is unconditional and may lag, so during the forwarding window a key rewritten or invalidated within a few seconds of a previous write via an old owner can keep the previous value until the next write or TTL expiry; frequently updated keys (counters via INCR, last-seen timestamps) are the realistic exposure. This is accepted rather than fixed: removing it would need versioned writes across the server and every SDK, or an extra joiner round trip on every forwarded write, for a stale that is bounded by TTL and needs a join, a double write with changed content and a lagging forward to coincide.
  3. When every node reports completion, discovery promotes the joiner into the served node list; clients pick it up on their next refresh. Until it is promoted, the joiner answers W to any client request that reaches it — no node list names it yet, but a connection a client dialed to the previous occupant of the same address can land on it — so the client refreshes and retries on an owner that has the key, instead of reading a miss from a node still being filled.
  4. A source keeps the copies it handed off, marked dead, until discovery confirms the join (the joiner shows up in its heartbeat acknowledgment, or in the roster of the next join's migrate request); an abandoned join restores them instead, so no key is lost to a half-finished handoff. A joiner that is promoted and gone again between two of a source's heartbeats never appears in a roster that source sees, so the heartbeat names such a joiner and discovery answers whether it has left; if it has, the source restores the copies and closes the window the same way.

Migrated-away entries are swept only after the join is confirmed, and the forwarding window stays open past completion to cover clients still routing with the older node list. Joins are serialized — one handoff at a time, cluster-wide — so a fleet started at once simply queues; a source that has finished one handoff accepts the next join's request while it is still forwarding for the previous one, and keeps forwarding to the earlier joiner until its own window ends — also when that later handoff is abandoned, its joiner evicted, or its transfer cut short.

Discovery without a single point of failure

The registry is deliberately soft state: nodes announce themselves and heartbeat continuously, so a discovery server's knowledge is always rebuildable from the nodes alone. That allows N independent replicas with zero coordination — no consensus, no leader election, no shared storage:

  • Every node and client is configured with the same replica list. Nodes heartbeat to all replicas; clients try their configured addresses in order.
  • Losing any replica — including the first-listed primary — costs neither cache traffic nor client bootstrap. Only joins pause until the primary is back, because exactly one orchestrator keeps handoffs simple.
  • A restarted replica answers B (busy) during a startup grace while live members re-announce, so clients never bootstrap from a half-recovered list; SDKs skip a busy replica like a dead one. A join requested during that grace is held until it ends, for the same reason: its handoff must come from every member, not from the few that have re-announced so far.

Pair this with a supervisor that restarts a dead replica (systemd, Kubernetes) and two replicas make discovery effectively always available.

Membership carries a second, per-node secret alongside the shared one: each node registers with a random membership token, and the frames that skip a node's wrong-node check — a join's M, a decommission's or re-replication's U/u — must present the receiver's token, so holding the cluster-wide shared secret alone doesn't let a client forge them. The flip side is deliberate: any registered node can fetch every member's token from discovery (the T frame), because a draining node must authorize handoffs to every peer, and a survivor re-replicating after an eviction must authorize them to owners it never met at registration time. Compromising one node therefore yields enough to impersonate any node in the cluster — the tokens narrow who can speak the internal frames from "anything holding the shared secret" down to "cluster members", not further. Size the blast radius accordingly: keep the data and operations ports internal (see Deployment's security groups), and treat a node-level compromise as a cluster-level event.

The proxy tier (optional)

Proxyless client-side sharding holds one connection per node per client process — a node-side connection count that grows with fleet size, capped by each node's connection limit. For large fleets, nanocached-proxy terminates many client connections and routes on their behalf: it fetches the roster from discovery, performs the same rendezvous-hash routing the SDKs do (namespaced keys included), fans writes out to all R owners, retries a stale-view W after a roster refresh, and fans c/F to every member. To a client it looks like a single node that owns every key, so any SDK pointed at one address — and any bare protocol client — works against it unchanged, with no ring view or discovery client of its own. Proxies are stateless and scale horizontally: each registers itself with discovery, and a client in proxy mode asks discovery for the proxy list and picks one — the only address anything ever needs is discovery's (a LB/VIP in front of the proxies works too). Clients that prefer cluster-direct connections keep working as before. Every client connection shares one tagged, pipelined backend connection per node, so the node-side connection count is the proxy count — not the fleet size — with bounded per-client and per-backend in-flight windows providing fairness and backpressure.

One documented limit of “looks like a single node”: the proxy enqueues every request on its backend connection in the order the client sent it, but a request the proxy has to retry (a stale-view W after a roster refresh, a replica fallback) is re-enqueued afterwards, outside that order. A client that pipelines a G for a key and, without awaiting its reply, an S for the same key on the same connection can — if the G lands on a stale view during a ring change — receive the value its own S just wrote. That is the same outcome an SDK’s own W retry produces in cluster-direct mode and is not a consistency violation (the write was already on the wire when the read was answered), so it is left as is rather than serialising same-key requests per connection. A client that needs the read to strictly precede the write awaits the G reply before sending the S.

Known limits

A ring change stalls a node for a few tens of milliseconds per million keys. Re-replication, a staged handoff, a decommission, and the ownership reclaim pass each begin by taking a snapshot of every live key the node holds, and that walk runs on the node’s single cache task, so requests that arrive during it wait. Measured in release builds at about 25 ms per million live keys (5 ms at 200k, 52 ms at 2M); at the default --max-memory of 256 MiB a node holds on the order of 2–3M small entries, so one membership change costs a few pauses of a few tens of milliseconds each (one per walker that runs, and the reclaim pass runs about twice per change: once after it, once when the grace window moves past the old membership) — the same order as the expiry sweep’s own periodic refill, and only on membership changes, never on the request path or on a timer. The snapshot itself is a transient allocation of 64 bytes per key that --max-memory does not account for (about 180 MiB at 3M keys), so leave that much headroom above the limit. Bounding it would need an ordered per-namespace key index that every write maintains; that standing cost on the hot path was judged not worth removing a rare, bounded pause. Size the node count so a single node’s keyspace stays in the low millions if even that pause matters to you.

Accepted behaviour

Each item below is a behaviour that was designed in or measured, judged, and left as it is. The sections above describe most of them in context; this list is the short form, one line per item with why it stays, so the next such decision has a place to go. Configuration facts (request size, connection caps, idle timeout) are in the per-page limits sections, not here.

Consistency and membership changes

  • During a join’s forwarding window, a key rewritten or invalidated within seconds of a write via an old owner may keep the previous value until the next write or TTL expiry (a lagging unconditional forward; relay coalescing). Accepted 2026-10-17: the stale is bounded by TTL and needs a join, a double write with changed content and a lagging forward to coincide, and removing it would need versioned writes in the server and every SDK. Revisit if a versioned write path is adopted for other reasons.
  • Re-replication handoff carries no version: when two survivors hold different copies, the first to reach the fresh node is kept, newer or not. A version would have to ride on every entry and every SDK write path; not adopted.
  • No anti-entropy sweep: diverged copies converge on the next write or TTL turnover, and a read-only key stays as it is. A sweep would be a standing cross-node scan for entries that TTL turns over anyway.
  • Two membership changes inside one drain window (two scale-ins at once, an eviction while a third drains) leave keys transiently below R. Each healer acts on one membership snapshot and none coordinate; retire nodes one at a time and the case does not arise.
  • A displaced copy loses its dead-copy mark on rewrite and is removed by the ownership reclaim pass after the 120 s grace; an eviction that flips membership back inside the grace makes it live again. The mark is released on rewrite because a mark that outlived its value once deleted fresh writes, and the grace exists so that a membership that flips back is not treated as a loss.
  • A replica leg refused with W by a live node is swallowed by the SDK; the key sits on one copy until its next write, and if that node dies first the newest value is lost. Seen on 1.5–17 % of writes in chaos runs that join, decommission and kill nodes back to back, spread unexplained; the cause was still unconfirmed on 2026-10-13 and the behaviour is accepted as it stands, to be revisited if a cause is found.
  • The proxy re-enqueues a retried request (stale-view W, replica fallback) outside the client’s send order; a pipelined G then S on one connection can read its own S. The same outcome an SDK’s own W retry produces in cluster-direct mode; serialising same-key requests per connection was judged not worth it. A client that needs the order awaits the G reply first.
  • A ring change pauses a node about 25 ms per million live keys (a snapshot walk on the single cache task), with a transient allocation of 64 bytes per key. Bounding it would need an ordered per-namespace key index maintained on every write; see Known limits above.
  • Hedged and fallback reads: a miss means the primary answered miss; a non-hedged read falls to the next owner only on connection failure. The primary’s answer is the answer; probing the other owners on a miss is what read repair, off by default, opts into.

Data model and operations

  • INCR and compare-and-set are as volatile as a plain set: eviction and TTL reclaim counters, and CAS is not a distributed lock since eviction breaks mutual exclusion. Replicas receive the result as a set, because replaying the operation could drift a replica from the primary.
  • The memory bound is approximate: key and value bytes plus a small per-entry overhead; allocator overhead is not metered. Leave headroom.
  • Replica-leg writes, read-repair writes and node-list refreshes fail silently, so that a dead replica never fails a write; the per-client counters (stats()) are the signal.
  • A standalone node has nobody to hand entries to and nothing is persisted: a restart is a cold cache.
  • Asymmetric port mapping (-p 9999:8356) is unsupported: it is NAT, which the cluster design excludes, since nodes are reached at the address they registered.
  • Any registered node can fetch every member’s token (T frame), because a draining node must authorize handoffs to peers it met after registration; registering a node is the trust step.
  • The operations endpoint (/healthz, /readyz, /metrics) is unauthenticated; bind it internally.
  • Cluster-internal frames are not frozen; a mixed-version cluster is a transient rolling-upgrade state only, discovery first. Policy, see Compatibility.

SDKs and adapters

  • The connect() forgotten-close warning is kept per address within a process, not per client instance, so several clients to one single address trip it even when each is closed in turn. Tracking per instance would never fire (a new instance has no previous connection), so the choice is this warning or none; kept. Share one client, or use a multi-address config.
  • Keyv adapter: has, the getMany family and iterator are deliberately omitted; JCache: honest subset (iterator, management and several configurations throw UnsupportedOperationException). The protocol has no key enumeration and no existence check short of a read; each adapter’s README lists what is omitted and why.
  • SDK production constants (timeouts, in-flight budgets) are mutable, documented-but-hidden test knobs so each SDK’s own test suite can shrink them; not an API, and not a connect option.
