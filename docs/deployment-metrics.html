Metrics collection

Every binary serves Prometheus-format metrics on its operations port. Which collector picks them up depends on the monitoring stack you already run, so this page is separate from the shape guides: it says what there is to collect and how the two kinds of metric behave once collected, then applies that to the single-node EC2 shape with the CloudWatch Agent, built, checked and torn down as shown. The ECS and EKS shapes are added here as each is verified.

What there is to collect

GET /metrics on --metrics-port answers in Prometheus text format (the endpoint, with its two probe paths, is described under what every deployment needs). A node exports fourteen series plus two per namespace; the ones to scale on are listed under metrics to scale on, and curl -s http://127.0.0.1:9356/metrics | grep -v '^#' prints the full set with its current values. Three things about them decide how a collector should be configured.

Gauges and counters. The _bytes, _entries and connections series are gauges: the value at the moment of the scrape. Everything ending in _total is a counter: a running total since the process started, which drops back to zero when it restarts. A Prometheus server stores counters as they are and rate() does the rest. A CloudWatch-style backend stores statistics per period, and the collector decides what number it hands over for a counter — the cumulative value, or the increase since the previous scrape. The CloudWatch Agent below hands over the increase, so Sum over a period is the number of operations in that period and a restart costs nothing but one dropped sample; a gauge’s Sum is meaningless there (four scrapes a minute of a 250-entry cache sum to 1,000), so gauges are read with Maximum or Average. Whichever backend you use, check which of the two it stores for a counter before building a dashboard on it.

Labels. The per-namespace series (nanocached_node_namespace_entries, …_namespace_used_bytes, and …_namespace_budget_bytes where a budget is set) carry a namespace label; nothing else does. The default namespace is the empty string, and a backend that turns labels into dimensions drops a series whose dimension value is empty — CloudWatch does — so the default namespace is read from the node-wide nanocached_node_entries and …_memory_used_bytes instead, and the labelled series cover the named namespaces. Each named namespace is one more series per metric, which is what a per-metric price is charged on.

Plain HTTP, no authentication. The operations endpoint is unauthenticated and never TLS, which is why the shape guides bind it inside the VPC. The least exposure is a collector on the same instance or in the same task scraping 127.0.0.1, which is what the EC2 shape below does; a central scraper is the alternative, reaching the port through the security-group rule the shape guides already carry (the operations port from inside the VPC, nothing wider).

The collectors this page covers are the ones whose output is a service you can read back from the command line: the CloudWatch Agent (EC2, below), the AWS Distro for OpenTelemetry collector (ECS, EKS) and a Prometheus server (EKS). Amazon Managed Service for Prometheus and Amazon Managed Grafana take the same scrape output through remote write; neither was available to the account these runs used, so they are not described here.

Single node on EC2 with the CloudWatch Agent

Start from the single-node EC2 guide: same network, same security groups, same instance. The agent runs on the node, scrapes 127.0.0.1:9356 every 15 s and publishes each scrape to CloudWatch Logs in the embedded metric format, from which CloudWatch extracts the metrics. Nothing inbound changes — the operations port is read over loopback.

IAM

One more managed policy on the instance role from that guide. CloudWatchAgentServerPolicy grants the log and metric writes the agent needs and nothing the node needs.

aws iam attach-role-policy --role-name $NAME-ec2 \
  --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy

The agent

Amazon Linux 2023 carries the agent in its own repository, so it is one more package on the dnf install line of node-user-data.sh (dnf install -y docker amazon-cloudwatch-agent), and the rest is appended after the systemctl enable --now nanocached-node line. Two files: a Prometheus scrape configuration with one static target, and the agent configuration that points at it and says which series to turn into metrics, under which dimensions.

cat > /opt/aws/amazon-cloudwatch-agent/etc/prometheus.yaml <<'PROM'
global:
  scrape_interval: 15s
scrape_configs:
  - job_name: nanocached-node
    static_configs:
      - targets: ['127.0.0.1:9356']
PROM
cat > /opt/aws/amazon-cloudwatch-agent/etc/nanocached.json <<'JSON'
{
  "logs": {
    "metrics_collected": {
      "prometheus": {
        "log_group_name": "nanocached-metrics",
        "prometheus_config_path": "/opt/aws/amazon-cloudwatch-agent/etc/prometheus.yaml",
        "emf_processor": {
          "metric_declaration_dedup": true,
          "metric_namespace": "nanocached",
          "metric_unit": {
            "nanocached_node_memory_used_bytes": "Bytes",
            "nanocached_node_memory_max_bytes": "Bytes",
            "nanocached_node_namespace_used_bytes": "Bytes",
            "nanocached_node_namespace_budget_bytes": "Bytes"
          },
          "metric_declaration": [
            {
              "source_labels": ["job"],
              "label_matcher": "^nanocached-node$",
              "dimensions": [["host", "namespace"]],
              "metric_selectors": ["^nanocached_node_namespace_"]
            },
            {
              "source_labels": ["job"],
              "label_matcher": "^nanocached-node$",
              "dimensions": [["host"]],
              "metric_selectors": [
                "^nanocached_node_(memory_used_bytes|memory_max_bytes|entries|connections|connections_max)$",
                "^nanocached_node_(hits|misses|sets|deletes|evictions|expirations|incrs|cas_sets|cas_deletes)_total$"
              ]
            }
          ]
        }
      }
    },
    "force_flush_interval": 5
  }
}
JSON
/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a fetch-config -m ec2 -s \
  -c file:/opt/aws/amazon-cloudwatch-agent/etc/nanocached.json

What each part is for:

  • metric_declaration is an allow-list: a scraped series that matches no declaration is written to the log group but never becomes a metric. The two entries give the per-namespace series a namespace dimension beside host and everything else host alone; the second entry names its series explicitly rather than matching ^nanocached_node_, which would also catch the namespace series and publish them a second time without their label. The host label is added by the agent and is the instance’s private DNS name (ip-10-0-0-65.ec2.internal in this run); the instance and job labels are also there to use as dimensions if you prefer them.
  • metric_namespace and log_group_name are set explicitly so the metrics land in a namespace of their own rather than the agent’s default and the log group has a name you will recognise at teardown. The agent creates the log group and one stream in it named after the job.
  • metric_unit attaches a unit to the byte gauges, so the console shows them scaled. Counters and counts are left without one.
  • fetch-config … -s validates the JSON, writes the agent’s own configuration, starts it and enables it, so it is back after a reboot without further arrangement.

From launch to a running agent took the same 80 s as the plain node (cloud-init reported Up 79.77 seconds; the agent’s own start time was one second earlier). The package that installed was amazon-cloudwatch-agent-1.300071.0.

Verifying

On the node, three things say the agent is scraping:

aws ssm send-command --instance-ids $NODE_ID --document-name AWS-RunShellScript \
  --parameters 'commands=["/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a status",
    "systemctl is-enabled amazon-cloudwatch-agent",
    "tail -1 /opt/aws/amazon-cloudwatch-agent/logs/configuration-validation.log"]'
# "status": "running", "configstatus": "configured" / enabled /
# The given config: /opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.toml is valid

A scrape that fails shows up only in /opt/aws/amazon-cloudwatch-agent/logs/amazon-cloudwatch-agent.log; the up series is not forwarded, so the file is the place to look when a metric stays flat.

From anywhere with the CLI, the metrics are readable in the same minute the agent starts. The host dimension is the value the agent attached:

aws cloudwatch list-metrics --namespace nanocached \
  --query 'Metrics[].[MetricName,Dimensions[].Value|join(`,`,@)]' --output text
HOST=ip-10-0-0-65.ec2.internal
aws cloudwatch get-metric-statistics --namespace nanocached \
  --metric-name nanocached_node_entries --dimensions Name=host,Value=$HOST \
  --start-time $(date -u -v-10M +%Y-%m-%dT%H:%M:%SZ) --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ) \
  --period 60 --statistics Maximum SampleCount \
  --query 'sort_by(Datapoints,&Timestamp)[].[Timestamp,Maximum,SampleCount]' --output text

In this run the node was given a known load first (200 keys written in one batch, 300 reads of which 100 missed, 50 keys written in a namespace called orders, after an earlier batch of the same 200 keys), so every number CloudWatch returned could be checked against /metrics:

  • list-metrics showed fourteen metrics under host and two under host,namespace with namespace=orders; the default namespace’s two series were, as said above, not published.
  • Gauges matched the endpoint: nanocached_node_entries Maximum 250, …_memory_used_bytes 48,592, …_memory_max_bytes 1,073,741,824, …_namespace_entries for orders 50, four samples in every minute.
  • Counters arrived as increases: nanocached_node_sets_total Sum 450 in the minute the writes happened and 0 in every minute after, against a cumulative 450 on the endpoint; …_hits_total 200 and …_misses_total 100 the same way. The first sample of each counter is dropped (three samples in that minute, not four) because an increase needs a predecessor.
  • A systemctl restart nanocached-node on the node (/readyz was 200 again within the same second), followed by 30 more writes: entries fell to 0 and rose to 30, sets_total summed to 30 for that minute — not negative, and not the 450 the counter had stood at before — and the sample count stayed at four a minute throughout. The agent carries on scraping across a restart of the node, and the restart is visible as the gauges dropping, not as a gap.

Each scrape is also one event in the log group, which is where the retention cost sits: a document with the fourteen values, the labels and the metric declarations, four times a minute per node. Set a retention period on nanocached-metrics once the metrics are confirmed; the metrics themselves are kept by CloudWatch on its own schedule and do not depend on the log events staying.

Teardown

The EC2 guide’s teardown, plus the log group and the extra policy before the role is deleted:

aws logs delete-log-group --log-group-name nanocached-metrics
aws iam detach-role-policy --role-name $NAME-ec2 \
  --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy

The metric namespace cannot be deleted: nanocached stays listed in the console with its last values until CloudWatch ages them out, at no charge once nothing is written to it.
