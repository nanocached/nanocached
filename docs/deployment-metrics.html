Metrics collection

Every binary serves Prometheus-format metrics on its operations port. Which collector picks them up depends on the monitoring stack you already run, so this page is separate from the shape guides: it says what there is to collect and how the two kinds of metric behave once collected, then applies that to the single-node EC2 shape with the CloudWatch Agent and to the clustered ECS shape with the AWS Distro for OpenTelemetry collector as a sidecar, each built, checked and torn down as shown. The EKS shape is added here once it is verified.

What there is to collect

GET /metrics on --metrics-port answers in Prometheus text format (the endpoint, with its two probe paths, is described under what every deployment needs). A node exports fourteen series plus two per namespace, a discovery server six; the ones to scale on are listed under metrics to scale on, and curl -s http://127.0.0.1:9356/metrics | grep -v '^#' prints the full set with its current values. Three things about them decide how a collector should be configured.

Gauges and counters. The _bytes, _entries and connections series are gauges: the value at the moment of the scrape. Everything ending in _total is a counter: a running total since the process started, which drops back to zero when it restarts. A Prometheus server stores counters as they are and rate() does the rest. A CloudWatch-style backend stores statistics per period, and the collector decides what number it hands over for a counter — the cumulative value, or the increase since the previous scrape. The CloudWatch Agent and the OpenTelemetry collector below both hand over the increase, so Sum over a period is the number of operations in that period, and after a restart the counter simply starts again from zero (the period’s Sum is the operations since the restart, never a negative number); a gauge’s Sum is meaningless there (four scrapes a minute of a 250-entry cache sum to 1,000), so gauges are read with Maximum or Average. Whichever backend you use, check which of the two it stores for a counter before building a dashboard on it.

Labels. The per-namespace series (nanocached_node_namespace_entries, …_namespace_used_bytes, and …_namespace_budget_bytes where a budget is set) carry a namespace label; nothing else does. The default namespace is the empty string, and a collector that turns labels into dimensions leaves out a series whose dimension value is empty — the output of both collectors below does — so the default namespace is read from the node-wide nanocached_node_entries and …_memory_used_bytes instead, and the labelled series cover the named namespaces. Each named namespace is one more series per metric, which is what a per-metric price is charged on.

Plain HTTP, no authentication. The operations endpoint is unauthenticated and never TLS, which is why the shape guides bind it inside the VPC. The least exposure is a collector on the same instance or in the same task scraping 127.0.0.1, which is what both shapes below do; a central scraper is the alternative, reaching the port through the security-group rule the shape guides already carry (the operations port from inside the VPC, nothing wider).

The collectors this page covers are the ones whose output is a service you can read back from the command line: the CloudWatch Agent (EC2, below), the AWS Distro for OpenTelemetry collector (ECS, below; EKS) and a Prometheus server (EKS). Amazon Managed Service for Prometheus and Amazon Managed Grafana take the same scrape output through remote write; neither was available to the account these runs used, so they are not described here.

Single node on EC2 with the CloudWatch Agent

Start from the single-node EC2 guide: same network, same security groups, same instance (the run behind this section built the node subnet and the node group only, and drove the load from the node itself; the application tier adds nothing to the metrics path). The agent runs on the node, scrapes 127.0.0.1:9356 every 15 s and publishes each scrape to CloudWatch Logs in the embedded metric format, from which CloudWatch extracts the metrics. Nothing inbound changes — the operations port is read over loopback.

IAM

One more managed policy on the instance role from that guide. CloudWatchAgentServerPolicy grants the log and metric writes the agent needs and nothing the node needs.

aws iam attach-role-policy --role-name $NAME-ec2 \
  --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy

The agent

Amazon Linux 2023 carries the agent in its own repository, so it is one more package on the dnf install line of node-user-data.sh (dnf install -y docker amazon-cloudwatch-agent), and the rest is appended after the systemctl enable --now nanocached-node line. Two files: a Prometheus scrape configuration with one static target, and the agent configuration that points at it and says which series to turn into metrics, under which dimensions.

cat > /opt/aws/amazon-cloudwatch-agent/etc/prometheus.yaml <<'PROM'
global:
  scrape_interval: 15s
scrape_configs:
  - job_name: nanocached-node
    static_configs:
      - targets: ['127.0.0.1:9356']
PROM
cat > /opt/aws/amazon-cloudwatch-agent/etc/nanocached.json <<'JSON'
{
  "logs": {
    "metrics_collected": {
      "prometheus": {
        "log_group_name": "nanocached-metrics",
        "prometheus_config_path": "/opt/aws/amazon-cloudwatch-agent/etc/prometheus.yaml",
        "emf_processor": {
          "metric_declaration_dedup": true,
          "metric_namespace": "nanocached",
          "metric_unit": {
            "nanocached_node_memory_used_bytes": "Bytes",
            "nanocached_node_memory_max_bytes": "Bytes",
            "nanocached_node_namespace_used_bytes": "Bytes",
            "nanocached_node_namespace_budget_bytes": "Bytes"
          },
          "metric_declaration": [
            {
              "source_labels": ["job"],
              "label_matcher": "^nanocached-node$",
              "dimensions": [["host", "namespace"]],
              "metric_selectors": ["^nanocached_node_namespace_"]
            },
            {
              "source_labels": ["job"],
              "label_matcher": "^nanocached-node$",
              "dimensions": [["host"]],
              "metric_selectors": [
                "^nanocached_node_(memory_used_bytes|memory_max_bytes|entries|connections|connections_max)$",
                "^nanocached_node_(hits|misses|sets|deletes|evictions|expirations|incrs|cas_sets|cas_deletes)_total$"
              ]
            }
          ]
        }
      }
    },
    "force_flush_interval": 5
  }
}
JSON
/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a fetch-config -m ec2 -s \
  -c file:/opt/aws/amazon-cloudwatch-agent/etc/nanocached.json

What each part is for:

  • metric_declaration is an allow-list: a scraped series that matches no declaration is written to the log group but never becomes a metric. The two entries give the per-namespace series a namespace dimension beside host and everything else host alone; the second entry names its series explicitly rather than matching ^nanocached_node_, which would also match the namespace series (what a series matched by two declarations becomes was not tried here). The host label is added by the agent and is the instance’s private DNS name (ip-10-0-0-65.ec2.internal in this run); the instance and job labels are also there to use as dimensions if you prefer them.
  • metric_namespace and log_group_name are set explicitly so the metrics land in a namespace of their own rather than the agent’s default and the log group has a name you will recognise at teardown. The agent creates the log group and one stream in it named after the job.
  • metric_unit attaches a unit to the byte gauges, so the console shows them scaled. Counters and counts are left without one.
  • fetch-config … -s validates the JSON, writes the agent’s own configuration, starts it and enables it, so it is back after a reboot without further arrangement.

From launch to a running agent took about 80 s (cloud-init reported Up 79.77 seconds; the agent’s own start time was one second earlier), about ten seconds more than the plain node in the EC2 guide. The package that installed was amazon-cloudwatch-agent-1.300071.0.

Verifying

On the node, three things say the agent is scraping:

aws ssm send-command --instance-ids $NODE_ID --document-name AWS-RunShellScript \
  --parameters 'commands=["/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a status",
    "systemctl is-enabled amazon-cloudwatch-agent",
    "tail -1 /opt/aws/amazon-cloudwatch-agent/logs/configuration-validation.log"]'
# "status": "running", "configstatus": "configured" / enabled /
# The given config: /opt/aws/amazon-cloudwatch-agent/etc/amazon-cloudwatch-agent.toml is valid

A scrape that fails shows up only in /opt/aws/amazon-cloudwatch-agent/logs/amazon-cloudwatch-agent.log; the up series is not forwarded, so the file is the place to look when a metric stays flat.

From anywhere with the CLI, the first datapoints carry the minute the agent started in (how soon after that they became readable was not timed in this run; the first query, six minutes later, found all of them). The host dimension is the value the agent attached:

aws cloudwatch list-metrics --namespace nanocached \
  --query 'Metrics[].[MetricName,Dimensions[].Value|join(`,`,@)]' --output text
HOST=ip-10-0-0-65.ec2.internal
aws cloudwatch get-metric-statistics --namespace nanocached \
  --metric-name nanocached_node_entries --dimensions Name=host,Value=$HOST \
  --start-time $(date -u -v-10M +%Y-%m-%dT%H:%M:%SZ) --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ) \
  # GNU date: $(date -u -d '-10 min' +%Y-%m-%dT%H:%M:%SZ)
  --period 60 --statistics Maximum SampleCount \
  --query 'sort_by(Datapoints,&Timestamp)[].[Timestamp,Maximum,SampleCount]' --output text

In this run the node was given a known load first (200 keys written in one batch, 300 reads of which 100 missed, 50 keys written in a namespace called orders, after an earlier batch of the same 200 keys), so every number CloudWatch returned could be checked against /metrics:

  • list-metrics showed fourteen metrics under host and two under host,namespace with namespace=orders; the default namespace’s two series were, as said above, not published.
  • Gauges matched the endpoint: nanocached_node_entries Maximum 250, …_memory_used_bytes 48,592, …_memory_max_bytes 1,073,741,824, …_namespace_entries for orders 50, four samples in every minute.
  • Counters arrived as increases: nanocached_node_sets_total Sum 450 in the minute the writes happened and 0 in every minute after, against a cumulative 450 on the endpoint; …_hits_total 200 and …_misses_total 100 the same way. The first sample of each counter is dropped (three samples in that minute, not four) because an increase needs a predecessor.
  • A systemctl restart nanocached-node on the node (/readyz was 200 again within the same second), followed by 30 more writes: entries fell to 0 and rose to 30, sets_total summed to 30 for that minute — not negative, and not the 450 the counter had stood at before — and the sample count stayed at four a minute throughout. The agent carries on scraping across a restart of the node, and the restart is visible as the gauges dropping, not as a gap.

Each scrape also lands in the log group as a few events, split by metric type and dimension set (one document for the gauges under host, one for the counters, one per named namespace), each carrying its values, the labels and the metric declarations, four times a minute per node — which is where the retention cost sits. Set a retention period on nanocached-metrics once the metrics are confirmed; the metrics themselves are kept by CloudWatch on its own schedule and do not depend on the log events staying.

Teardown

The EC2 guide’s teardown, plus the log group and the extra policy before the role is deleted:

aws logs delete-log-group --log-group-name nanocached-metrics
aws iam detach-role-policy --role-name $NAME-ec2 \
  --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy

The metric namespace cannot be deleted: nanocached stays listed in the console with its last values until CloudWatch ages them out, at no charge once nothing is written to it.

Cluster on ECS with the OpenTelemetry collector

Start from the ECS guide: same network, security groups, Cloud Map name, cluster and services. Each task — the discovery task and every node task — gets a second container, the AWS Distro for OpenTelemetry collector, which scrapes localhost inside the task’s network namespace every 15 s and writes each scrape to CloudWatch Logs in the embedded metric format, exactly as the agent does on EC2. One configuration serves both kinds of task: the job name and the port are environment variables the sidecar sets, and the configuration refers to them.

IAM

Two changes to the ECS guide’s roles. The tasks now need a role of their own, because the collector calls CloudWatch — the first shape on this site where they do — and CloudWatchAgentServerPolicy is the one managed policy that covers the log and metric writes:

aws iam create-role --role-name $NAME-ecs-task --tags Key=Project,Value=$NAME \
  --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow",
    "Principal":{"Service":"ecs-tasks.amazonaws.com"},"Action":"sts:AssumeRole"}]}'
aws iam attach-role-policy --role-name $NAME-ecs-task \
  --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy

And the execution role’s inline policy must cover the collector’s configuration parameter as well as the auth secret, since both are injected through secrets:

aws iam put-role-policy --role-name $NAME-ecs-execution --policy-name read-parameters \
  --policy-document "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",
    \"Action\":\"ssm:GetParameters\",
    \"Resource\":[\"arn:aws:ssm:$AWS_REGION:${ACCOUNT}:parameter/$NAME/auth-secret\",
                 \"arn:aws:ssm:$AWS_REGION:${ACCOUNT}:parameter/$NAME/otel-config\"]}]}"

The collector’s configuration

Save this as otel-config.yaml and put it in Parameter Store as a plain String (it is well under the 4 KB a standard parameter holds):

receivers:
  prometheus:
    config:
      global:
        scrape_interval: 15s
      scrape_configs:
        - job_name: ${env:NANOCACHED_JOB}
          static_configs:
            - targets: ['localhost:${env:NANOCACHED_METRICS_PORT}']
processors:
  resourcedetection:
    detectors: [ecs]
    timeout: 5s
  resource:
    attributes:
      - key: TaskId
        from_attribute: aws.ecs.task.id
        action: insert
  batch:
    timeout: 5s
exporters:
  awsemf:
    namespace: nanocached
    log_group_name: nanocached-metrics
    log_stream_name: ${env:NANOCACHED_JOB}/{TaskId}
    dimension_rollup_option: NoDimensionRollup
    resource_to_telemetry_conversion:
      enabled: true
    metric_descriptors:
      - metric_name: nanocached_node_memory_used_bytes
        unit: Bytes
        overwrite: true
      - metric_name: nanocached_node_memory_max_bytes
        unit: Bytes
        overwrite: true
      - metric_name: nanocached_node_namespace_used_bytes
        unit: Bytes
        overwrite: true
      - metric_name: nanocached_node_namespace_budget_bytes
        unit: Bytes
        overwrite: true
    metric_declarations:
      - dimensions: [[TaskId, namespace]]
        metric_name_selectors: ["^nanocached_node_namespace_"]
      - dimensions: [[TaskId]]
        metric_name_selectors:
          - "^nanocached_node_(memory_used_bytes|memory_max_bytes|entries|connections|connections_max)$"
          - "^nanocached_node_(hits|misses|sets|deletes|evictions|expirations|incrs|cas_sets|cas_deletes)_total$"
          - "^nanocached_discovery_"
service:
  pipelines:
    metrics:
      receivers: [prometheus]
      processors: [resourcedetection, resource, batch]
      exporters: [awsemf]
aws ssm put-parameter --name /$NAME/otel-config --type String \
  --value file://otel-config.yaml --tags Key=Project,Value=$NAME

What each part is for:

  • The per-task dimension. With a localhost target, the instance label is the same on every task, so it cannot tell tasks apart. resourcedetection asks the task metadata endpoint for the task’s identity, the resource processor copies the task ID into an attribute called TaskId, and resource_to_telemetry_conversion makes that attribute available to the declarations as a dimension. The zone, task family and revision come along as well and are in every log event, should you want them as dimensions instead.
  • metric_declarations is the allow-list, as on EC2: TaskId alone for the node and discovery series, TaskId and namespace for the per-namespace ones. NoDimensionRollup stops the exporter from also publishing each metric without dimensions.
  • metric_descriptors attaches a unit to the byte gauges; without it every metric arrived with no unit (the receiver does not infer one from a _bytes suffix).
  • ${env:…} is expanded by the collector when it reads the configuration, including inside the embedded Prometheus block, and {TaskId} in log_stream_name is filled in by the exporter — so one parameter gives each task its own job name, port and log stream.
  • The configuration is read once, when the task starts (it arrives as an environment variable). A change to the parameter reaches a task only when the task is replaced — a new deployment (aws ecs update-service --force-new-deployment), or, as in this run, one task stopped and replaced by the service: the unit descriptors were added to the parameter just before the stop, and the replacement task published units while the untouched task did not.

Task definitions

The sidecar is the same container in both task definitions, with two environment variables and the log prefix changed. For td-node.json, add it after the node container; for td-discovery.json, with nanocached-discovery, 9357 and a discovery-otel prefix:

{
  "name": "otel-collector",
  "image": "public.ecr.aws/aws-observability/aws-otel-collector@sha256:7968fb60db6a2390a47ba6a2df029745638486e285c9b2487da1b722d0855a3e",
  "essential": false,
  "environment": [{"name": "NANOCACHED_JOB", "value": "nanocached-node"},
                  {"name": "NANOCACHED_METRICS_PORT", "value": "9356"}],
  "secrets": [{"name": "AOT_CONFIG_CONTENT",
               "valueFrom": "arn:aws:ssm:us-east-1:123456789012:parameter/nanocached/otel-config"}],
  "logConfiguration": {"logDriver": "awslogs", "options": {"awslogs-group": "/ecs/nanocached",
                       "awslogs-region": "us-east-1", "awslogs-stream-prefix": "node-otel"}}
}
  • essential: false: a collector that exits must not take the cache container down with it. The reverse is handled by ECS — when the essential container stops, the task stops.
  • No dependsOn: the collector starts beside the node and scrapes from the moment it is ready. In this run the node was listening one second before the collector’s first scrape, and neither sidecar logged a failed scrape; a slower node start would show as a short run of failed scrapes in the sidecar’s log, nothing worse.
  • The image is pinned by digest, as the nanocached images are; this is the 0.50.0 release of the collector. docker buildx imagetools inspect against a newer tag prints the digest to move to.
  • The node task is registered with --memory 2048 instead of the guide’s 1024 (the next size Fargate offers at 512 CPU units), so the collector is not carved out of the 512 MiB cache’s headroom; and both task definitions take --task-role-arn for the new role:
TASK_ARN=arn:aws:iam::${ACCOUNT}:role/${NAME}-ecs-task
aws ecs register-task-definition --family $NAME-node --network-mode awsvpc \
  --requires-compatibilities FARGATE --cpu 512 --memory 2048 \
  --execution-role-arn $EXEC_ARN --task-role-arn $TASK_ARN \
  --tags key=Project,value=$NAME --container-definitions file://td-node.json

Services are created exactly as in the ECS guide. In this run discovery’s Cloud Map record was discoverable 92 s after its create-service, and the node service was steady 2 min 6 s after that first create-service; both node tasks joined on their first attempt.

Verifying

Each sidecar has its own log stream under /ecs/$NAME (prefix node-otel or discovery-otel); the line to look for is Everything is ready. Begin running and processing data, and a configuration the collector cannot parse ends the stream with the error before that line. The metrics then carry the task ID:

aws cloudwatch list-metrics --namespace nanocached \
  --query 'Metrics[?Dimensions[?Name==`TaskId`]].[MetricName,Dimensions[].Value|join(`,`,@)]' --output text
TASK=$(aws ecs list-tasks --cluster $NAME --service-name node --query 'taskArns[0]' --output text | sed 's#.*/##')
aws cloudwatch get-metric-statistics --namespace nanocached \
  --metric-name nanocached_node_entries --dimensions Name=TaskId,Value=$TASK \
  --start-time $(date -u -v-10M +%Y-%m-%dT%H:%M:%SZ) --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ) \
  --period 60 --statistics Maximum SampleCount \
  --query 'sort_by(Datapoints,&Timestamp)[].[Timestamp,Maximum,SampleCount]' --output text
  # GNU date: $(date -u -d '-10 min' +%Y-%m-%dT%H:%M:%SZ)

In this run the cluster was given a known load from the application tier through discovery (2,000 keys written in batches of 200, the same 2,000 read back in batches, 500 reads of keys that did not exist, 100 keys written in a namespace called orders) and every number was checked against each task’s /metrics, read over 9356 from the application instance:

  • The discovery task’s six series were listed under its task ID about two minutes after its collector started, with the first datapoints in the collector’s start minute; the node tasks’ fourteen, plus two for orders, likewise carried their start minute and were readable at the first query made two and a half minutes later (not polled finer than that).
  • Gauges matched per task: nanocached_node_entries Maximum 2,100 on both tasks (under a replication factor of 2, both hold every key), …_memory_used_bytes 426,442, …_namespace_entries for orders 100, four samples a minute.
  • Counters arrived as increases, and the split between tasks was the ownership split: …_sets_total Sum 2,100 on each task in the write minute and 0 after; …_hits_total 1,014 and 986; …_misses_total 265 and 235 — each the task’s own cumulative value, since the whole load fell inside one minute. As on EC2, the first sample of each counter is the baseline and is not published.
  • nanocached_discovery_members read 2 under the discovery task’s ID.

What a task replacement looks like is the ECS-specific question, and the run answered it with aws ecs stop-task on one node task. ECS had a replacement running and healthy 73 s after the stop (the new node joined 49 s after it), and the surviving node handed it every key under the replication factor, so the new task’s entries read 2,100 from its first sample. Three things follow for a dashboard:

  • The stopped task’s ID simply stops updating — one sample in its last minute — and the new ID appears in the next minute. A widget pinned to one task ID goes dark; graph the dimension with a SEARCH expression or an aggregate across TaskId instead.
  • The 2,100 writes that filled the new node were the migration transfer, which the node counts in …_sets_total; but they happened before the collector’s first sample, so as increases they are invisible (Sum 0 in the new task’s first minutes). A burst that completes before the first scrape is never seen by a delta-reporting collector.
  • nanocached_discovery_members dipped to 1 and back to 2 inside the stop minute (Minimum 1, Maximum 2), which is the one place the event is visible as a value rather than as a dimension changing.

Teardown

The ECS guide’s teardown, plus the task role, the configuration parameter and the metrics log group:

aws iam detach-role-policy --role-name $NAME-ecs-task \
  --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy
aws iam delete-role --role-name $NAME-ecs-task
aws ssm delete-parameter --name /$NAME/otel-config
aws logs delete-log-group --log-group-name nanocached-metrics
