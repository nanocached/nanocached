TLS

Three flags, the same on every binary, decide which segments of a deployment are encrypted. This page says what each one covers, why a node’s certificate must name its IP address, how to mint and distribute self-signed certificates on AWS, and how to rotate them — then applies all of it to the single-node and the clustered EC2 shapes and to the ECS and EKS shapes, each built, checked and torn down exactly as shown.

What each flag encrypts

Every process accepts connections, and most of them also dial out. --tls-cert/--tls-key (a PEM chain and its key) turn on TLS for everything the process accepts, with no plaintext fallback: a plaintext client gets a TLS alert and the connection is closed. --tls-ca (a PEM file of one or more CA certificates) turns on TLS for everything the process dials, trusting only those certificates — not the system trust store, since a private cluster’s certificates are not publicly issued. The two are independent, and a process with only one of them set warns at start-up that the other direction is plaintext. The SDKs take the same two pieces as options: tls and, for anything that is not publicly issued, ca. There are no client certificates: a peer is authenticated by the shared secret, and TLS adds confidentiality and the server’s identity on top.

Application → discovery (node list)discovery --tls-cert/--tls-keySDK tls + cathe address in the SDK’s configuration: a hostname or an IP
Node → discovery (registration, heartbeats)discovery --tls-cert/--tls-keynode --tls-cathe node’s --discovery address
Discovery → node (join and eviction orders)node --tls-cert/--tls-keydiscovery --tls-cathe IP the node registered from

Proxy → node, proxy → discoveryas aboveproxy --tls-caas above

By shape: a single node has one segment, so the node gets --tls-cert/--tls-key and nothing else. A cluster has all of the first five, so discovery and every node get all three flags. A proxy tier adds the last two, and the proxy gets all three as well. The operations endpoint (--metrics-port) is plain HTTP in every case; it was checked over HTTP on the TLS node below, and the usual advice of keeping it inside the VPC is the whole of its protection.

Names in certificates

Nodes are addressed by IP. Discovery records the source IP of a node’s registration connection, hands that address to the SDKs in the node list and to the other nodes in rosters, and dials it itself for join and eviction orders. Every one of those connections verifies the node’s certificate against that IP, so a node’s certificate must carry its IP address in subjectAltName. A certificate with only a DNS name fails with certificate not valid for name "10.0.0.10" on discovery and an IP address mismatch on the SDKs. The same holds for a proxy that applications reach through the proxy list discovery serves: that list is registration IPs too.

Discovery itself is different: nodes dial the address given as --discovery and applications dial the address in their configuration, so a discovery certificate names whatever that is — a DNS name if you front discovery with one, an IP otherwise. A proxy behind a load balancer, reached by the balancer’s name, likewise names that name. The ECS shape below is the one where discovery is reached by a DNS name, and its certificate carries that name beside the task’s IP; on EKS the name is a Service, and the single label disc that nodes dial is in the SAN as itself.

The IP has to be known when the certificate is minted. On EC2 that is a matter of choosing it: run-instances takes --private-ip-address, and the shape below fixes the node’s address that way. Where an address is only assigned when the process starts — an ECS task — the certificate has to be minted then, from a CA whose certificate the applications already trust; the ECS shape below does that with an init container.

Self-signed certificates

A self-signed certificate is a leaf that is its own trust anchor: the same file is the node’s --tls-cert and every dialler’s ca. It needs three extensions that OpenSSL’s defaults do not give it — CA:FALSE (a self-signed certificate is otherwise marked as a CA, which rustls refuses to accept as a server’s leaf), a subjectAltName with the IP, and serverAuth — and the -subj is then only a label:

NODE_PRIVATE_IP=10.0.0.10
openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout node-key.pem -out node-cert.pem \
  -subj "/CN=nanocached-node" \
  -addext "subjectAltName=IP:$NODE_PRIVATE_IP" \
  -addext "basicConstraints=critical,CA:FALSE" \
  -addext "keyUsage=critical,digitalSignature,keyEncipherment" \
  -addext "extendedKeyUsage=serverAuth"

The result is about 1.2 KB of certificate and 1.7 KB of key, which matters for the distribution step. Because the system trust store is never consulted (not by the servers, and not by an SDK once ca is set), a self-signed deployment always carries the certificate to the application tier explicitly; an SDK configured with tls alone verifies against the platform store and rejects the node with CERTIFICATE_VERIFY_FAILED, which is the right outcome for a certificate nobody vouched for.

A cluster needs one certificate per host, each with its own IP, and a trust anchor that does not change every time a host does. That is a private CA: a self-signed CA certificate whose key stays with the operator, and a leaf per host signed by it. The flags are the same; --tls-ca and ca take the CA certificate instead of the leaf, and a leaf can be reissued without the application tier learning a new file. Minting the CA and one leaf:

# once: the CA. Its key never leaves the operator's machine.
openssl req -x509 -newkey rsa:2048 -nodes -days 3650 -keyout ca-key.pem -out ca.pem \
  -subj "/CN=nanocached CA" \
  -addext "basicConstraints=critical,CA:TRUE,pathlen:0" \
  -addext "keyUsage=critical,keyCertSign,cRLSign"
# per host: a leaf for its address.
IP=10.0.0.11
openssl req -new -newkey rsa:2048 -nodes -keyout host-$IP-key.pem -out host-$IP.csr \
  -subj "/CN=nanocached-$IP"
printf 'subjectAltName=IP:%s\nbasicConstraints=critical,CA:FALSE\nkeyUsage=critical,digitalSignature,keyEncipherment\nextendedKeyUsage=serverAuth\n' \
  $IP > host-$IP.ext
openssl x509 -req -in host-$IP.csr -CA ca.pem -CAkey ca-key.pem -CAcreateserial -days 365 \
  -extfile host-$IP.ext -out host-$IP-cert.pem

A host serves its leaf alone (no chain: the dialler trusts the CA directly), and a leaf from this CA and a self-signed leaf from the section above do not trust each other, so a deployment picks one model. A managed CA (AWS Private CA) fits the same slot — it signs the leaves, its certificate is the trust anchor — and was not run for this page.

Distribution

Two files per process, with different sensitivity: the certificate is public, the key is a secret. Systems Manager Parameter Store holds both as parameters under one prefix — the certificate as a String, the key as a SecureString encrypted with the account’s default key — and the standard tier’s 4 KB limit per parameter fits the sizes above with room to spare. A third parameter carries the certificates the application tier should trust, which is the same file today and becomes a bundle during rotation:

aws ssm put-parameter --name /nanocached/tls/node-cert --type String       --value file://node-cert.pem
aws ssm put-parameter --name /nanocached/tls/node-key  --type SecureString --value file://node-key.pem
aws ssm put-parameter --name /nanocached/tls/trust     --type String       --value file://node-cert.pem

With a private CA the layout gains a level: the CA certificate is the trust parameter, and each host’s pair sits under its address, which the host reads from the instance metadata service to pick its own:

aws ssm put-parameter --name /nanocached/tls/ca                  --type String       --value file://ca.pem
aws ssm put-parameter --name /nanocached/tls/hosts/10.0.0.11/cert --type String       --value file://host-10.0.0.11-cert.pem
aws ssm put-parameter --name /nanocached/tls/hosts/10.0.0.11/key  --type SecureString --value file://host-10.0.0.11-key.pem

An instance whose role carries AmazonSSMManagedInstanceCore — the policy the deployment shapes already attach for Session Manager — can read all three, decryption included; no further IAM statement was needed in the run below. The node fetches its two before every start, so a replacement instance and a restart after rotation take the same path. Applications fetch the trust parameter the same way, and nothing on the application side ever needs the key. Secrets Manager would hold the key in the same manner, read with get-secret-value in place of get-parameter --with-decryption; that path was not run for this page. Where the fetched files land matters once an instance is imaged: the cluster shape below writes them to /run, a tmpfs that is never in a snapshot, and the same choice is right for a single node that will ever be imaged.

On ECS nothing is pre-minted, so the parameters carry the CA instead of leaves: the trust bundle, and the signing certificate and key an init container uses to mint the task’s own leaf at start. The signing certificate is a parameter of its own rather than “the first certificate in the trust bundle” because during a CA rotation the trust bundle holds two certificates and the signing key matches only one of them. ECS injects all three into the init container as environment variables through the task definition’s secrets, read by the execution role:

aws ssm put-parameter --name /nanocached/tls/ca           --type String       --value file://ca.pem
aws ssm put-parameter --name /nanocached/tls/signing-cert --type String       --value file://ca.pem
aws ssm put-parameter --name /nanocached/tls/signing-key  --type SecureString --value file://ca-key.pem

That puts the CA’s private key within reach of every task’s init container, where on EC2 it never left the operator’s machine. It is the price of minting at start, and the init limits it: the key exists as an environment variable of a container that deletes its copy from the shared volume and exits before the node starts.

On Kubernetes the same three files are two Secrets — the trust bundle in one, the signing pair in the other — mounted read-only into the init container, and only the trust Secret is mounted by the applications. A Secret is readable by anything that can mount Secrets in its namespace, so the signing Secret stays in the cluster’s namespace and applications in another namespace get a copy of the trust Secret alone:

kubectl -n nanocached create secret generic nanocached-tls-ca      --from-file=ca.pem=ca.pem
kubectl -n nanocached create secret generic nanocached-tls-signing --from-file=signing-cert.pem=ca.pem --from-file=signing-key.pem=ca-key.pem

Rotation

Certificate and key are read once, at start, so a rotation is a restart: replace the files (here, overwrite the parameters and let the fetch step pick them up) and restart the process. With a self-signed leaf the trust anchor rotates with it, which forces an order on the steps: the application tier has to trust old and new before the node switches, or every connection fails the moment it does.

  1. Mint the new pair with the same IP. Publish old + new, concatenated, as the trust parameter, and let the applications pick it up (an application reads its ca file when it constructs a client; the check program below was simply run again).
  2. Overwrite the node’s certificate and key parameters with the new pair and restart the node. From restart to /readyz answering again took 1.7 s, including the parameter fetch; a standalone node comes back empty either way.
  3. Once no application still trusts only the old certificate, publish the new certificate alone as the trust parameter.

Checked on the single-node shape below: with the node still on the old certificate, both the bundle and the old file alone connect; after the restart, the bundle connects and the old file alone fails with CERTIFICATE_VERIFY_FAILED.

With a private CA there are two rotations. A leaf rotates alone: overwrite that host’s two parameters and restart its processes; nothing else changes, because every dialler trusts the CA, not the leaf. The CA rotates in the three steps above, applied to every process at once: publish old + new as the trust parameter and restart every process (each reads --tls-ca at start), re-fetch on the applications, then reissue each host’s leaf under the new CA and restart it, host by host; publishing the new CA alone, and the restart that picks it up, can wait for the next routine restart. Both were run on the cluster shape below.

On ECS a restart is a deployment, and every task start mints a fresh leaf, so leaf rotation is update-service --force-new-deployment and nothing more; a leaf’s lifetime only matters for a task that lives that long. CA rotation is the same three steps with the parameters: trust := both CAs and a forced deployment of discovery and node; signing pair := the new CA and another forced deployment; trust := the new CA alone whenever the next deployment happens. Each forced deployment of the node service is a rolling replacement in which every old task drains and every new one joins, so the data survives it. Run on the ECS shape below. On Kubernetes the deployment is kubectl rollout restart, and a changed Secret is applied with kubectl create secret --dry-run=client -o yaml | kubectl apply -f -; a pod that mounts the trust Secret sees the new file within about a minute, but an application reads its ca file when it constructs a client, so count on the restart, not on the propagation. Run on the EKS shape below.

Single node on EC2, with TLS

This is the single-node shape with one segment encrypted: application to node. Everything not shown here — the VPC, the two security groups, the instance role with AmazonSSMManagedInstanceCore, the application server’s subnet — is as in that guide; the differences are the ones below, and the whole thing was built from an empty account, checked, rotated and torn down in one sitting.

Before the instance exists, pick its address, mint the certificate for it and store the three parameters. The address is the first usable one in the node subnet (10.0.0.0/24’s .1–.3 are reserved by AWS; .10 is chosen for legibility):

NODE_PRIVATE_IP=10.0.0.10
# the openssl command from "Self-signed certificates", then:
aws ssm put-parameter --name /nanocached/tls/node-cert --type String       --value file://node-cert.pem
aws ssm put-parameter --name /nanocached/tls/node-key  --type SecureString --value file://node-key.pem
aws ssm put-parameter --name /nanocached/tls/trust     --type String       --value file://node-cert.pem

The user-data gains a fetch script that systemd runs before every start, and the unit gains a read-only volume and the two flags. The container runs as uid 10001, so the script hands the files to that user; the key is 0600, the certificate 0644, and both are written to a temporary name and renamed so a restart never sees a half-written key. The region comes from the instance metadata service rather than any CLI default:

#!/bin/bash
set -euo pipefail
dnf install -y docker
systemctl enable --now docker
install -d -m 700 /etc/nanocached
cat > /etc/nanocached/env <<'ENV'
NANOCACHED_AUTH_SECRET=change-me
ENV
chmod 600 /etc/nanocached/env
cat > /usr/local/bin/nanocached-fetch-tls <<'FETCH'
#!/bin/bash
# Pull this node's certificate and private key from Parameter Store into a
# directory the container's user (uid 10001) can read. Runs before every start.
set -euo pipefail
TOKEN=$(curl -s -X PUT http://169.254.169.254/latest/api/token -H 'X-aws-ec2-metadata-token-ttl-seconds: 60')
REGION=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/placement/region)
install -d -m 750 -o 10001 -g 10001 /etc/nanocached/tls
aws ssm get-parameter --region "$REGION" --name /nanocached/tls/node-cert \
  --query Parameter.Value --output text > /etc/nanocached/tls/cert.pem.new
aws ssm get-parameter --region "$REGION" --name /nanocached/tls/node-key --with-decryption \
  --query Parameter.Value --output text > /etc/nanocached/tls/key.pem.new
chown 10001:10001 /etc/nanocached/tls/cert.pem.new /etc/nanocached/tls/key.pem.new
chmod 644 /etc/nanocached/tls/cert.pem.new
chmod 600 /etc/nanocached/tls/key.pem.new
mv /etc/nanocached/tls/cert.pem.new /etc/nanocached/tls/cert.pem
mv /etc/nanocached/tls/key.pem.new /etc/nanocached/tls/key.pem
FETCH
chmod 755 /usr/local/bin/nanocached-fetch-tls
cat > /etc/systemd/system/nanocached-node.service <<'UNIT'
[Unit]
Description=nanocached node
After=docker.service
Requires=docker.service
[Service]
ExecStartPre=-/usr/bin/docker rm -f nanocached-node
ExecStartPre=/usr/bin/docker pull ghcr.io/nanocached/nanocached-node@sha256:2104f8263c6f909d734fb6302a74bbedd5d583c14fb73713268ef4627fad5337
ExecStartPre=/usr/local/bin/nanocached-fetch-tls
ExecStart=/usr/bin/docker run --rm --name nanocached-node \
  --network host \
  --env-file /etc/nanocached/env \
  --volume /etc/nanocached/tls:/etc/nanocached/tls:ro \
  ghcr.io/nanocached/nanocached-node@sha256:2104f8263c6f909d734fb6302a74bbedd5d583c14fb73713268ef4627fad5337 \
  --host 0.0.0.0 --port 8356 --metrics-port 9356 \
  --tls-cert /etc/nanocached/tls/cert.pem --tls-key /etc/nanocached/tls/key.pem \
  --max-memory 1073741824
ExecStop=/usr/bin/docker stop -t 30 nanocached-node
Restart=always
RestartSec=2
[Install]
WantedBy=multi-user.target
UNIT
systemctl daemon-reload
systemctl enable --now nanocached-node

The launch adds the fixed address; the rest of the command is unchanged:

NODE_ID=$(aws ec2 run-instances --image-id $AMI_ID --instance-type t3.small \
  --subnet-id $NODE_SUBNET_ID --private-ip-address $NODE_PRIVATE_IP --security-group-ids $NODE_SG \
  --iam-instance-profile Name=$NAME-ec2 --user-data file://node-user-data.sh \
  --tag-specifications "ResourceType=instance,Tags=[$TAG,{Key=Name,Value=$NAME-node}]" \
  --query 'Instances[0].InstanceId' --output text)

On the node, the same three checks as before plus the files the fetch produced:

aws ssm send-command --instance-ids $NODE_ID --document-name AWS-RunShellScript \
  --parameters 'commands=["systemctl is-active nanocached-node",
    "curl -s -o /dev/null -w healthz=%{http_code}\\\\n http://127.0.0.1:9356/healthz",
    "curl -s -o /dev/null -w readyz=%{http_code}\\\\n http://127.0.0.1:9356/readyz",
    "ls -ln /etc/nanocached/tls"]'
# active / healthz=200 / readyz=200
# -rw-r--r--. 1 10001 10001 1201 cert.pem
# -rw-------. 1 10001 10001 1705 key.pem

The unit was active by the time Systems Manager could reach the instance, as without TLS; the fetch adds two API calls to the start-up path and nothing noticeable.

From the application server, the SDK needs the trust file and tls; the file comes from the trust parameter, which the instance role can read:

aws ssm get-parameter --region us-east-1 --name /nanocached/tls/trust \
  --query Parameter.Value --output text > /etc/nanocached-trust.pem
client = await NanocachedClient.connect(
    [("10.0.0.10", 8356)],
    auth_secret="change-me",
    tls=True,
    ca="/etc/nanocached-trust.pem",
)

Run that way with the Python SDK at 0.4.6, a cache check (set, get, delete) succeeds. The three ways of getting it wrong each fail where they should: an unrelated self-signed certificate as ca and tls=True with no ca (the platform trust store) both fail the handshake with CERTIFICATE_VERIFY_FAILED, and a plaintext connection is answered with a TLS alert and closed — the SDK reports unexpected response to A, and nc shows the alert’s first bytes (025 003 003). One detail of the application host: Amazon Linux 2023’s default python3 is 3.9, below the SDK’s 3.11 floor, so pip finds no version; dnf install python3.11 python3.11-pip and python3.11 -m pip install nanocached is what worked. The operations endpoint answered /metrics over plain HTTP from the application server, and from outside the app group both ports were refused, as before.

Rotation followed the three steps above: a second pair minted for the same address, the trust parameter overwritten with both certificates and re-fetched on the application server (both the bundle and the old file alone still connected), then the node’s two parameters overwritten and systemctl restart nanocached-node: /readyz was back in 1.7 s, openssl x509 -in /etc/nanocached/tls/cert.pem -noout -serial on the node showed the new serial, the bundle connected and the old file alone failed verification.

Teardown is the single-node guide’s sequence plus the parameters, one call each:

for p in node-cert node-key trust; do aws ssm delete-parameter --name /nanocached/tls/$p; done

Cluster on EC2, with TLS

This is the clustered shape — a seed running discovery and a node at 10.0.0.11, nodes at other fixed addresses, growth from an image — with every segment encrypted: application to node and to discovery, node to discovery, discovery to node, node to node. Every process gets all three flags, each host gets a leaf from the private CA, and the application tier trusts the CA certificate. The network, security groups and role are the cluster guide’s; what follows is the difference, built and checked from an empty account with a seed, two nodes (one added from the image) and an application server, then torn down.

Before the instances exist: the CA, a leaf per address you are about to launch, and the parameters. The seed’s one leaf (IP:10.0.0.11) serves both its discovery and its node; one mint per host, not per process.

# the CA and the leaves, from "Self-signed certificates", for 10.0.0.11 and 10.0.0.12; then:
aws ssm put-parameter --name /nanocached/tls/ca --type String --value file://ca.pem
for IP in 10.0.0.11 10.0.0.12; do
  aws ssm put-parameter --name /nanocached/tls/hosts/$IP/cert --type String       --value file://host-$IP-cert.pem
  aws ssm put-parameter --name /nanocached/tls/hosts/$IP/key  --type SecureString --value file://host-$IP-key.pem
done

The user-data differs from the cluster guide’s in three places. The fetch is its own oneshot unit, because on the seed two services would otherwise run it at once into the same files; both services Requires= and After= it, so a plain systemctl restart of either re-fetches first. The files go to /run/nanocached/tls, a tmpfs, so that the image taken from a node below never contains a private key. And the host picks its own parameters by its address from the instance metadata service, which is what lets a node from the image start with no user-data at all. The seed’s user-data in full:

Growing the cluster keeps the cluster guide’s image (taken from a node with --no-reboot; 94 s to available here) and changes what a launch from it needs: an address chosen in advance, a leaf for it, its two parameters, and --private-ip-address on run-instances. The order matters, and this run tried it the wrong way round on purpose: launched before its parameters existed, the new instance failed its fetch (ParameterNotFound), and because the node unit Requires= the fetch, the node unit failed to start and stayed down — Restart=always retries a service that exited, not one whose dependency failed, so nothing loops and nothing recovers by itself. Putting the parameters and systemctl start nanocached-node over Run Command was the fix: /readyz answered 3 s later, discovery registered and promoted the node, the seed’s node handed it 1,336 of the 2,000 keys over TLS (its journal’s migration completed line, the new node’s accepted connection from 10.0.0.11), the member count read 3, and every key still read back.

Rotating a leaf is a restart of that host: overwrite its two parameters with a new pair from the same CA and systemctl restart nanocached-node. The restart is the planned leave from the cluster guide and then a join: the node handed its 1,336 entries off within the drain budget, systemctl restart returned after 22 s, /readyz answered a second later, discovery logged the leave and a fresh registration, openssl x509 -in /run/nanocached/tls/cert.pem -noout -serial showed the new serial, and the 2,000 keys read back complete. On the seed, the two units read the same files, so a leaf rotation there restarts both.

Rotating the CA is the three-step order from Rotation, and this run did the first two. Step one: the trust parameter overwritten with both CA certificates (2.3 KB, still inside the 4 KB tier), then one restart per process, discovery first — systemctl restart nanocached-discovery took 19 s to /readyz, the seed’s node journal showed re-registered with discovery and the member count stayed 3 — then each node in turn, 23 s each, ca.pem holding two certificates on every host afterwards; the application tier, still trusting only the old CA at this point, kept reading all 2,000 keys throughout, and then re-fetched the bundle. Step two, for one host: a leaf for 10.0.0.13 issued by the new CA, its two parameters overwritten, the node restarted; it rejoined, openssl x509 -noout -issuer on its certificate named the new CA, and the application tier with the bundle read all 2,000 keys. Step three — the new CA alone as the trust parameter and one more round of restarts — is step one again with a smaller file, and was left for the next routine restart.

Teardown is the cluster guide’s (instances, image and snapshot, role, groups, network) plus one delete-parameter per parameter: the CA and two per host.

Cluster on ECS, with TLS

This is the ECS shape — discovery and nodes as Fargate services across two zones, discovery behind the Cloud Map name disc.nanocached.local — with every segment encrypted. A Fargate task’s address is assigned when it starts and the node image has no openssl, so each task mints its own leaf in an init container: a stock Alpine image that reads the task’s IP from the container metadata endpoint, signs a leaf for it with the signing pair from Parameter Store, writes the files to a volume shared with the main container, and exits before the main container starts. Discovery’s leaf additionally carries the Cloud Map name, which is what nodes and applications verify it by. The network, security groups, Cloud Map namespace, cluster and log group are the ECS guide’s; the differences follow, built and checked from an empty account with one discovery task, two node tasks grown to three, and an application server, then torn down.

Parameters and the execution role. Beside the auth secret, the three from Distribution; the execution role’s ssm:GetParameters statement lists all four ARNs. The SecureString signing key needed nothing beyond that statement, as the auth secret did not.

The init script, saved as tls-init.sh. It installs openssl on the way in (one network step per task start; a prebuilt image with openssl removes it), prints the address it minted for and nothing else, since its output goes to CloudWatch Logs, and leaves the files owned by the node’s user:

set -eu
apk add --no-cache openssl >/dev/null
IP=$(wget -qO- "$ECS_CONTAINER_METADATA_URI_V4" | sed -n 's/.*"IPv4Addresses":[[:space:]]*\[[[:space:]]*"\([0-9.]*\)".*/\1/p' | head -1)
[ -n "$IP" ] || { echo "tls-init: no task IP in metadata" >&2; exit 1; }
cd /tls
printf '%s\n' "$NANOCACHED_TLS_CA" > ca.pem
printf '%s\n' "$NANOCACHED_TLS_SIGNING_CERT" > signing-cert.pem
printf '%s\n' "$NANOCACHED_TLS_SIGNING_KEY" > signing-key.pem
openssl req -new -newkey rsa:2048 -nodes -keyout key.pem -out leaf.csr -subj "/CN=nanocached-$IP" 2>/dev/null
printf 'subjectAltName=IP:%s%s\nbasicConstraints=critical,CA:FALSE\nkeyUsage=critical,digitalSignature,keyEncipherment\nextendedKeyUsage=serverAuth\n' "$IP" "${TLS_EXTRA_SAN:-}" > leaf.ext
openssl x509 -req -in leaf.csr -CA signing-cert.pem -CAkey signing-key.pem -CAcreateserial -days 365 -extfile leaf.ext -out cert.pem 2>/dev/null
rm -f signing-cert.pem signing-key.pem leaf.csr leaf.ext signing-cert.srl
chown 10001:10001 ca.pem cert.pem key.pem; chmod 644 ca.pem cert.pem; chmod 600 key.pem
echo "tls-init: minted a certificate for $IP"

Cluster on EKS, with TLS

This is the EKS shape — a discovery Deployment behind the disc Service, a node Deployment spread across two zones — with every segment encrypted, by the same device as on ECS: a pod’s address is assigned when it is scheduled, so an init container mints the pod’s leaf at start. Three things change from ECS. The pod IP comes from the downward API rather than a metadata endpoint; the CA material comes from two Secrets mounted as files rather than from parameters injected as variables; and the shared volume is an emptyDir backed by memory, so the leaf and key never touch a worker’s disk. Discovery’s leaf names the Service in every form a dialler might use: disc, which the nodes dial, through disc.nanocached.svc.cluster.local for an application in another namespace. The cluster itself is the EKS guide’s eksctl configuration unchanged; the workload below was applied to it, checked from a pod in the namespace, grown, rotated and torn down.

The Secrets, from the files minted under Self-signed certificates, as in Distribution; the auth Secret is the EKS guide’s.

The init script is the ECS one with the address and the files coming from the pod:

apk add --no-cache openssl >/dev/null
[ -n "${POD_IP:-}" ] || { echo "tls-init: POD_IP is not set" >&2; exit 1; }

cp /tls-ca/ca.pem ca.pem
openssl req -new -newkey rsa:2048 -nodes -keyout key.pem -out leaf.csr -subj "/CN=nanocached-$POD_IP" 2>/dev/null
printf 'subjectAltName=IP:%s%s\nbasicConstraints=critical,CA:FALSE\nkeyUsage=critical,digitalSignature,keyEncipherment\nextendedKeyUsage=serverAuth\n' "$POD_IP" "${TLS_EXTRA_SAN:-}" > leaf.ext
openssl x509 -req -in leaf.csr -CA /tls-signing/signing-cert.pem -CAkey /tls-signing/signing-key.pem -days 365 -extfile leaf.ext -out cert.pem 2>/dev/null
rm -f leaf.csr leaf.ext
chown 10001:10001 ca.pem cert.pem key.pem; chmod 644 ca.pem cert.pem; chmod 600 key.pem
echo "tls-init: minted a certificate for $POD_IP"
